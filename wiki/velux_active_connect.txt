====== VELUX Active Connect ======

**Status:** Stable  
**Version:** 1.1.0  
**Minimum LoxBerry:** 4.0.0

Version 1.1.0 bündelt die seit dem letzten offiziellen Stable-Release 1.0.0 vorgenommenen Verbesserungen an Sicherheit, Reboot-Robustheit, UDP, Logging und responsiver Weboberfläche.

VELUX Active Connect verbindet VELUX ACTIVE / VELUX App Control mit LoxBerry und Loxone. Das Plugin erkennt Homes, Räume und Geräte über die verwendete VELUX-/Netatmo-Schnittstelle, liest Statuswerte aus und überträgt ausgewählte Werte per UDP an Loxone. Unterstützte Geräte können zusätzlich aus dem Plugin oder per UDP von Loxone gesteuert werden.

===== Übersicht =====

Die Integration trennt Oberfläche, Konfiguration, Scheduler, API-Kommunikation und UDP-Kommunikation voneinander:

<code>
cron.01min -> Scheduler -> Intervallprüfung -> Worker -> VELUX API -> UDP an Loxone
</code>

Steuerbefehle laufen separat über einen dauerhaft überwachten Listener:

<code>
Loxone -> UDP -> Listener/Daemon -> Validierung -> VELUX API
</code>

Die CGI-Seiten dienen der Oberfläche und interaktiven Aktionen. Periodische API-Abfragen laufen nicht im CGI.

===== Funktionen =====

  * VELUX ACTIVE Cloud-Anbindung
  * automatische Home-, Raum- und Geräteerkennung
  * Gateway-Kopplung für signierte Steuerbefehle
  * Access-/Refresh-Token-Verwaltung
  * Temperatur, Feuchtigkeit, CO₂, Helligkeit, Luftqualität und weitere von VELUX gemeldete Werte
  * Regenstatus, sofern von VELUX bereitgestellt
  * frei wählbare UDP-Rückmeldungen für Loxone
  * wahlweise alle Werte oder nur Änderungen senden
  * Boolean-Werte konsequent als ''1'' oder ''0''
  * Heartbeat
  * UDP-Steuerung von Loxone zu VELUX
  * Prüfung erlaubter UDP-Absender
  * Fenstersteuerung: AUF, STOP, ZU und Position, sofern vom Gerät unterstützt
  * Wiederaufnahme der VELUX ACTIVE Automatik
  * Plugin Aktiv/Inaktiv
  * Scheduler/Worker mit Lock gegen parallele API-Läufe
  * UDP-Listener mit Watchdog und automatischem Neustart
  * update-sichere Einstellungen, Tokens, UDP-Auswahl und Gateway-Daten
  * zentrale Versionsanzeige über ''plugin.cfg''
  * Loxone-Export mit konfiguriertem UDP-Präfix und individuellen UDP-Namen
  * Logging und Diagnose

===== Voraussetzungen =====

  * LoxBerry 4.0.0 oder neuer
  * VELUX ACTIVE / VELUX App Control Installation
  * gültiges VELUX Benutzerkonto
  * Netzwerk-/Internetzugriff des LoxBerry zur VELUX-Schnittstelle
  * Netzwerkverbindung zwischen LoxBerry und Loxone Miniserver
  * für signierte Befehle ein erreichbares und gekoppeltes VELUX Gateway

===== Installation =====

  - ''VELUX_Active_Connect_v1.1.0.zip'' über die LoxBerry Pluginverwaltung installieren.
  - **VELUX Active Connect** öffnen.
  - Unter **Einstellungen** die VELUX-Zugangsdaten eintragen.
  - Loxone Miniserver und UDP-Ports auswählen.
  - Abrufintervall konfigurieren.
  - Einstellungen speichern.
  - **VELUX Daten jetzt abrufen** ausführen.
  - Unter **UDP Messages** die gewünschten Werte auswählen.
  - Falls für Steuerbefehle erforderlich, das VELUX Gateway koppeln.
  - Auf der Seite **Status** Verbindung, Kopplung und letzten erfolgreichen Abruf kontrollieren.

===== Anmeldung =====

Für die Anmeldung werden die Zugangsdaten des VELUX ACTIVE / VELUX App Control Kontos verwendet.

Das Plugin nutzt nach erfolgreicher Anmeldung bevorzugt den Refresh-Token zur Token-Erneuerung. Nur wenn eine Erneuerung nicht möglich ist, wird der vorhandene Login-Fallback verwendet.

Zugangsdaten werden bei einem erfolgreichen Token-Refresh nicht automatisch gelöscht, damit eine spätere erneute Anmeldung oder Gateway-Aktion weiterhin möglich bleibt.

===== Gateway-Kopplung =====

Für bestimmte signierte Steuerbefehle kann eine Gateway-Kopplung erforderlich sein.

Nach erfolgreicher Kopplung zeigt die Statusseite sinngemäß:

<code>
API: Verbunden
Gateway: Gekoppelt
</code>

Die Kopplungsinformationen und Signierschlüssel bleiben bei Updates erhalten.

===== Einstellungen =====

==== VELUX ACTIVE ====

  * E-Mail
  * Passwort
  * Abrufintervall
  * Plugin aktiv/inaktiv

==== Loxone UDP – Rückmeldungen ====

Datenrichtung:

<code>
VELUX ACTIVE -> LoxBerry -> Loxone
</code>

Konfigurierbar sind insbesondere:

  * UDP-Ausgabe aktiv/inaktiv
  * Ziel-Miniserver aus der LoxBerry-Grundkonfiguration
  * UDP-Sendeport
  * UDP-Präfix
  * Heartbeat
  * Sendeverhalten: alle Werte oder nur Änderungen

==== Loxone UDP – Steuerung ====

Datenrichtung:

<code>
Loxone -> LoxBerry -> VELUX ACTIVE
</code>

Konfigurierbar sind insbesondere:

  * UDP-Steuerung aktiv/inaktiv
  * UDP-Empfangsport
  * Befehlspräfix, Standard ''velux.cmd''
  * erlaubte Absender / LoxBerry-Miniserver

===== Geräte und Werte =====

Nach einem erfolgreichen Abruf werden die von VELUX erkannten Homes, Räume, Module und Geräte verarbeitet. Die verfügbaren Werte werden dynamisch ermittelt.

Unter **UDP Messages** kann jeder relevante Wert einzeln aktiviert oder deaktiviert und – sofern angeboten – mit einem individuellen UDP-Namen versehen werden.

Beispiele:

<code>
velux.module.dachfenster_bad.position=50
velux.module.velux_gateway.reachable=1
velux.room.bad.temperature=23.7
</code>

Boolean-Werte werden für Loxone als ''1'' bzw. ''0'' übertragen.

===== UDP =====

Das Grundschema für Rückmeldungen lautet:

<code>
velux.<gerät>.<wert>=<value>
</code>

Bestehende veröffentlichte Namen bleiben aus Kompatibilitätsgründen erhalten. Der tatsächliche Präfix kann in den Einstellungen angepasst werden.

UDP-Telegramme werden als sauberes ''key=value'' ohne zusätzliche Steuerzeichen übertragen.

==== Heartbeat ====

Beispiel:

<code>
velux.heartbeat=1
</code>

''1'' bedeutet betriebsbereit. Ein Fehlerzustand wird entsprechend als ''0'' signalisiert, sofern Heartbeat aktiviert ist.

===== Steuerung =====

Das Grundschema für Steuerbefehle lautet:

<code>
velux.cmd.<gerät>.<command>=<value>
</code>

Nur Befehle, die das jeweilige Gerät unterstützt, sollten verwendet werden.

Typische Befehle:

<code>
velux.cmd.dachfenster_bad.open=1
velux.cmd.dachfenster_bad.stop=1
velux.cmd.dachfenster_bad.close=1
velux.cmd.dachfenster_bad.position=50
</code>

Für API-Aufrufe notwendige Kontexte wie ''home_id'' werden vom Plugin berücksichtigt.

===== VELUX-Automatik =====

Manuelle Fenstersteuerung kann den VELUX-Modus auf ''manual'' setzen. Das Plugin unterstützt deshalb die Wiederaufnahme/Freigabe der VELUX-Automatik.

Befehl aus Loxone:

<code>
velux.cmd.velux_active.automation=1
</code>

Intern wird die vorhandene VELUX-Logik zur Freigabe der Automatik verwendet, unter anderem der Zustand:

<code>
mode=algo_available
</code>

Bedeutung wichtiger Textzustände:

  * ''manual'' = manueller Betrieb
  * ''algo_available'' = Automatik ist freigegeben/verfügbar
  * ''algo_active'' = VELUX-Automatik greift aktuell aktiv ein

Diese Zustände sind Textwerte und müssen in Loxone entsprechend als Text ausgewertet bzw. per Befehlserkennung weiterverarbeitet werden.

===== Loxone-Beispiele =====

==== Virtueller UDP-Ausgang ====

In Loxone Config einen virtuellen UDP-Ausgang mit der IP-Adresse des LoxBerry und dem konfigurierten Empfangsport anlegen.

Beispiel Befehle bei EIN:

<code>
velux.cmd.dachfenster_bad.open=1
velux.cmd.dachfenster_bad.close=1
velux.cmd.dachfenster_bad.stop=1
</code>

Für eine Position kann beispielsweise gesendet werden:

<code>
velux.cmd.dachfenster_bad.position=50
</code>

Bei virtuellen UDP-Ausgängen **Verbindung nach Senden schließen** aktivieren.

==== UDP-Eingang / Statuswerte ====

Für numerische Werte wird der jeweilige Wert hinter dem Gleichheitszeichen ausgewertet, beispielsweise:

<code>
velux.module.dachfenster_bad.position=50
</code>

Textzustände wie ''algo_active'' sollten in Loxone über passende Befehlserkennung/Textauswertung verarbeitet werden.

===== Status =====

Die Statusseite unterscheidet verständlich zwischen:

  * Plugin aktiv/inaktiv
  * API verbunden/nicht verbunden
  * Gateway gekoppelt/nicht gekoppelt
  * letzter erfolgreicher Abruf
  * nächster geplanter Lauf
  * letzter Steuerbefehl bzw. Steuerstatus, sofern vorhanden
  * Fehlerzustand / Diagnose
  * erkannte Geräte

Die Plugin-Version wird zentral aus ''plugin.cfg'' gelesen. Es gibt keine hardcodierte Versionsnummer in CGI-Seiten.

===== Weboberfläche =====

Alle Buttons und Navigationselemente sind für normale, aktive, Hover-, Fokus- und deaktivierte Zustände mit expliziten Vorder-/Hintergrundfarben definiert.

Störende geerbte ''text-shadow'', ''box-shadow'', Filter oder Hintergrundeffekte werden für kritische UI-Elemente neutralisiert, damit Titel und aktive Buttons lesbar bleiben.

Die Oberfläche ist responsiv aufgebaut. Auf Smartphones werden breite Tabellen als einzelne Karten dargestellt, Formulare einspaltig angeordnet und Bedienelemente auf die verfügbare Breite angepasst. Die Einstellungen sind in VELUX-Konto, Abruf/Plugin, UDP-Statuswerte, UDP-Steuerung und Gateway-Kopplung gegliedert.

Unter **UDP Messages** werden UDP-Status, Heartbeat, Sendeverhalten, Ziel, Port, Präfix und die Anzahl aktivierter Werte angezeigt. Zusätzlich können alle erkannten Werte gemeinsam aktiviert oder deaktiviert werden.

===== Logging =====

Das Log enthält abhängig von der Aktion unter anderem:

  * API-Abrufe und Fehler
  * Token-/Anmeldefehler
  * erkannte Werte
  * gesendete UDP-Telegramme inklusive vollständigem ''key=value'', Ziel-Miniserver und Port
  * empfangene und validierte Steuerbefehle
  * verworfene nicht erlaubte UDP-Absender
  * Scheduler-/Worker-Läufe
  * Listener-/Watchdog-Ereignisse
  * Gateway-/Steuerfehler

Ein erfolgreicher Abruf aktualisiert den Zeitstempel des letzten erfolgreichen Laufs. Fehlgeschlagene Abrufe werden beim nächsten Scheduler-Lauf erneut versucht.

===== Scheduler und Listener =====

Periodische Aufgaben laufen über:

<code>
cron.01min -> Scheduler -> Intervallprüfung -> Worker
</code>

Der Worker besitzt einen Lock gegen parallele Läufe.

Der UDP-Steuerungs-Listener läuft dauerhaft als Daemon. Ein Watchdog prüft den Listener und startet ihn bei Bedarf neu. Die PID-Datei wird erst nach erfolgreichem UDP-Port-Bind veröffentlicht.

Nach einem LoxBerry- oder Plugin-Neustart werden temporär noch nicht verfügbare Netzwerk-/API-/UDP-Ressourcen nicht als dauerhafter Erfolg behandelt. Der nächste Scheduler-/Watchdog-Lauf versucht erneut.

===== Fehlerbehebung =====

==== API nicht verbunden ====

  * Internet-/Netzwerkverbindung des LoxBerry prüfen
  * VELUX-Zugangsdaten prüfen
  * Log auf Token-/Loginfehler prüfen
  * Datenabruf erneut auslösen

==== Gateway nicht gekoppelt ====

  * Gateway-Erreichbarkeit prüfen
  * Kopplung erneut durchführen
  * Log auf Signierungs-/Pairingfehler prüfen

==== UDP-Werte kommen nicht an ====

  * UDP-Ausgabe aktivieren
  * richtigen Miniserver auswählen
  * UDP-Sendeport prüfen
  * gewünschte Werte unter **UDP Messages** aktivieren
  * Firewall/Netzwerk prüfen
  * Log prüfen

==== UDP-Steuerung funktioniert nicht ====

  * UDP-Steuerung aktivieren
  * Empfangsport prüfen
  * Miniserver als erlaubten Absender auswählen
  * virtuellen UDP-Ausgang in Loxone prüfen
  * **Verbindung nach Senden schließen** aktivieren
  * Log prüfen

==== Fenster bleibt auf manual ====

Folgenden Befehl senden:

<code>
velux.cmd.velux_active.automation=1
</code>

==== AUF oder Position schlägt fehl ====

  * prüfen, ob das Gerät den Befehl unterstützt
  * Gateway-Kopplung prüfen
  * Gateway-Erreichbarkeit prüfen
  * Log auf API-/Signierungsfehler prüfen

===== Sicherheit =====

UDP besitzt keine eigene Verschlüsselung und sollte ausschließlich im lokalen vertrauenswürdigen Netzwerk verwendet werden.

Der Listener prüft die Absender-IP gegen die konfigurierten erlaubten Miniserver. Nicht erlaubte Absender werden verworfen.

Tokens und Zugangsdaten werden in der Plugin-Konfiguration gehalten. Die automatische Token-Erneuerung nutzt bevorzugt den Refresh-Token. Credential-Felder werden defensiv verarbeitet, damit fehlende Werte nicht zu CGI-/HTTP-500-Fehlern führen.

===== Backup und Update =====

Bei Updates bleiben insbesondere erhalten:

  * VELUX Zugangsdaten
  * Access-/Refresh-Tokens
  * Home-/Gateway-Zuordnung
  * Gateway-Kopplungsinformationen und Signierschlüssel
  * ausgewählter Loxone Miniserver
  * UDP-Sende-/Empfangseinstellungen
  * UDP-Auswahl und individuelle UDP-Namen
  * Abrufintervall
  * Pluginstatus
  * Listener-/Absenderkonfiguration

Vor einem Update wird der UDP-Listener sauber beendet. PID-Dateien des alten Prozesses werden nicht wiederverwendet. Nach dem Update startet der Watchdog den Listener mit dem neuen Code neu, sofern UDP-Steuerung aktiviert ist.

Die aktuelle ''plugin.cfg'' des neuen Pakets wird nach dem Restore erneut übernommen, damit keine alte Versionsnummer aus einem Backup erhalten bleibt.
